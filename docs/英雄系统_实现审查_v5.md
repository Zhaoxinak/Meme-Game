## 0. 一句话

英雄系统有一个状态机 bug 让英雄变成**永久无敌的僵尸**，把单轮战斗从 12.0s 拖到 42.9s，42% 的轮次撞满 75s 时限。修完回到 **18.1s、超时率 0.6%**，对称性保持（z=1.29）。

| | 单轮耗时 均值/中位 | 撞时限轮次 | 对称性 z |
|---|---|---|---|
| 无英雄基线 | 12.0s / 11.6s | 0 / 160 | 1.81 |
| 修复前 | 42.9s / 29.6s | 68 / 160 (42.5%) | 1.29 |
| **修复后** | **18.1s / 14.5s** | **1 / 160 (0.6%)** | **1.29** |

顺带暴露了一个**设计层面的冲突**：v5 §5 纪律③「英雄不死亡，只退场」与战斗结束条件「一方全灭」直接打架——双方各有一个永生英雄时，结束条件永远不成立。解法是让胜负由军团决定，英雄不计入全灭判定（F9）。

## 3. 逐条规格

### F1 · 英雄无敌僵尸（P0）

**为什么**：`damageUnit` 守卫 `if (u.dead || u.dying) return`，而 `dying` 一旦置真就没人清除。

```js
// utils.js:219（retreatHero 内）与 update.js:426（返场内），同一行补丁
hero.hp = Math.max(1, Math.round(hero.maxHp * HERO_CFG.retreatHpPct));
hero.dying = false;          // ← 新增
```

**注意**：F1 与 F2 重叠——F2 落地后英雄根本不会进 `dying` 路径，这行是**防御性冗余**。两处都留，因为 `dying` 是通用字段，别指望没人再动它。

### F2 · 英雄生死分歧（P0）

**为什么**：同一个英雄，被近战打死就退场、被远程打死就真死。玩家的行为不该决定系统的存在方式。

```js
// utils.js:99-104，当前
if (u.hp <= 0) {
  u.hp = 0;
  if (u.state !== "knocked") finishKill(u, attacker);
  else u.dying = true;
}

// 改为
if (u.hp <= 0) {
  u.hp = 0;
  // 英雄不走死亡结算：一律退场（v5 §5 纪律③）。
  // 原逻辑下「最后一击带不带击退」决定英雄是退场还是真死 —— 系统行为不该由攻击类型决定。
  if (FLAGS.hero && u.isHero && u.state !== "retreat") { retreatHero(u); return; }
  if (u.state !== "knocked") finishKill(u, attacker);
  else u.dying = true;
}
```

**连带影响**（要明确，别悄悄改语义）：

- 英雄不再调用 `finishKill` → **不计入 `G.pKills`/`G.eKills`、不加 combo、不触发爆破手自爆**
- 退场的击杀播报由 `retreatHero` 内的 `pushFeed` 负责（已实现）
- 若将来要"击杀英雄计分"，应单独加字段，不要复用小兵的击杀计数

### F3 · `heroOf` 过滤退场 + 拆分实体查找（P1）

```js
// utils.js:149，当前只过滤 dead/dead-state
function heroOf(side) {
  if (!FLAGS.hero) return null;
  for (const u of G.units) {
    if (u.isHero && u.side === side && !u.dead && u.state !== "dead") return u;
  }
  return null;
}

// 改为
/* 英雄实体（含退场中的）。退场英雄仍在 G.units 里，只是不该参与战斗结算。 */
function heroEntity(side) {
  if (!FLAGS.hero) return null;
  for (const u of G.units) {
    if (u.isHero && u.side === side && !u.dead && u.state !== "dead") return u;
  }
  return null;
}
/* 在场可战斗的英雄：退场中（state==="retreat"）返回 null，
   光环 / 免击退 / AI 放大招全部自然失效，不需要在每个调用点重复判状态。 */
function heroOf(side) {
  const u = heroEntity(side);
  return u && u.state !== "retreat" ? u : null;
}
```

### F4 · 重写 `updateHero`（P1）

当前问题：末尾 `if (hero.state === "retreat") continue;` 是循环体最后一行（完全无效），导致退场期间士气照回、AI 照常放大招（特效在 `x=-60` 场外播放，玩家看不见但资源已消耗）。

```js
function updateHero(dt) {
  for (const side of ["player", "enemy"]) {
    const hs = heroState(side); if (!hs) continue;
    if (hs.ultT > 0) hs.ultT = Math.max(0, hs.ultT - dt);
    if (hs.ultCd > 0) hs.ultCd = Math.max(0, hs.ultCd - dt);

    const ent = heroEntity(side);

    // ① 退场中：只走返场倒计时，不回士气、不放招、不参与任何战斗结算
    if (ent && ent.state === "retreat") {
      if (hs.retreatT > 0) {
        hs.retreatT = Math.max(0, hs.retreatT - dt);
        if (hs.retreatT === 0) {
          ent.x = side === "player" ? 45 : CONFIG.worldW - 45;
          ent.y = 240;
          ent.hp = Math.max(1, Math.round(ent.maxHp * HERO_CFG.retreatHpPct));
          ent.dying = false;                    // F1 防御性冗余
          ent.state = "move"; ent.stateT = 0;
          addEffect("ring", ent.x, ent.y, { r: 60, color: "#c9b037", glow: "#fff3c1" });
        }
      }
      continue;
    }

    // ② 场上无英雄（未生成 / 已被清理）：仍推进退场倒计时
    if (!ent) {
      if (hs.retreatT > 0) hs.retreatT = Math.max(0, hs.retreatT - dt);
      continue;
    }

    // ③ 在场：士气自然回复 + AI 满气自动放大招
    if (hs.ultT === 0) hs.morale = Math.min(HERO_CFG.moraleMax, hs.morale + HERO_CFG.moraleRegen * dt);
    if (side === "enemy" && FLAGS.heroUlt && hs.ultT === 0 && hs.ultCd === 0 && hs.morale >= HERO_CFG.moraleMax) {
      castHeroUlt("enemy");
    }
  }
}
```

**同时删除** `update.js:435-440` 那个空 `if` 块（含 `G.hero._spawned` 判断，该字段从未被写入，是彻底的死代码）。

### F5 · `heroOf` 按帧缓存（P3）

`heroOf` 在每次伤害结算时被 `heroAuraReduce` 调用，内部遍历全单位。峰值 80 单位 × 每秒上百次伤害 = O(n²)。

```js
let _heroCacheT = -1;
const _heroCache = { player: null, enemy: null };

function heroEntity(side) {
  if (!FLAGS.hero) return null;
  if (G.t !== _heroCacheT) {                       // G.t 每帧递增 → 每帧只算一次
    _heroCacheT = G.t;
    _heroCache.player = null; _heroCache.enemy = null;
    for (const u of G.units) {
      if (!u.isHero || u.dead || u.state === "dead") continue;
      if (!_heroCache[u.side]) _heroCache[u.side] = u;
    }
  }
  return _heroCache[side] || null;
}
```

缓存只活一帧，英雄死亡/退场最迟下一帧生效，不影响正确性。

### F9 · 英雄阻塞「一方全灭」判定（P0，施工中暴露）

**这是设计冲突，不是实现 bug**——但必须解决，否则 F2 无法落地。

F2 让英雄永不真死。而战斗结束条件是 `pa === 0 || ea === 0`（一方全灭）。英雄永远在 `G.units` 里（`dead=false`，退场只是 `state="retreat"`），于是**双方各有一个永生英雄 → 结束条件永不成立**。

实测：F1-F8 修完但 F9 未修时，**160/160 轮全部打满 75s**——比修复前更糟。

```js
// update.js 胜负检测
let pa = 0, ea = 0;
for (const u of G.units) {
  if (u.dead || u.hp <= 0) continue;
  // 英雄不参与「全灭」判定：胜负由军团决定，英雄是加成不是胜负条件（v5 §5 纪律①）
  if (FLAGS.hero && u.isHero) continue;
  if (u.side === "player") pa++; else ea++;
}
```

**设计立场**：军团战是核心，英雄是调味。让两个英雄互砍到死来决定一轮胜负，既慢又偏离主题。

### F10 · 退场状态被通用单位 AI 覆写（P0，施工中暴露）

英雄永不 `dead`，所以不再被通用循环的 `if (u.dead) continue` 跳过，跟着走寻敌逻辑后 `state` 被覆写成 `"move"`/`"attack"`——退场状态形同虚设，返场倒计时永远走不完（实测 `state=retreat` 一帧后变 `move`）。

```js
// update.js 单位主循环开头
if (u.dead) { u.stateT -= dt; u.deathT += dt; continue; }
// 英雄退场中：已离场，不参与任何战斗 AI
if (u.isHero && u.state === "retreat") continue;
```

**这条是测试逼出来的**——手写测试断言「近战致死 → state 应为 retreat」时当场抓到。没有断言就不会发现。

## 7. 附：僵尸 bug 的发现过程

### 7.1 现场

单轮打到 70s，场上剩 3 个单位，两英雄相距 43.3px、`state="attack"`、互相锁定。逐帧 dump：

```
帧 | A.hp  B.hp | A.attackT  B.attackT | dist | A.state B.state | A.swing
  7 |   240   240 |         0       167 |  43.3 | attack  attack  | -0.62
  8 |   240   240 |      1000       150 |  43.3 | attack  attack  | 0.38    ← attack() 执行了
  9 |   240   240 |       983       133 |  43.3 | attack  attack  | 0.36    ← 但 HP 没掉
```

`swing=0.38` 说明 `attack()` 确实跑到了 `u.swing = 0.38`，紧接着的 `damageUnit` 却在守卫处 return 了。

### 7.2 根因链

| # | 位置 | 事实 |
|---|------|------|
| 1 | `utils.js:99-103` | HP 归零且 `state === "knocked"` → 只置 `dying=true`，**不走 `finishKill`** |
| 2 | `update.js:417` | `updateHero` 检测 `hp <= 0` → 调 `retreatHero` |
| 3 | `utils.js:219` | 回血到 50%，**从不清除 `dying`** |
| 4 | `utils.js:78` | 守卫 `if (u.dead \|\| u.dying) return` → 永久免疫 |
| 5 | 现场铁证 | 双方 HP 都恰好 `240 = 480 × 0.5`，正是 `retreatHpPct` |

近战 `knock=90` 必然触发击退 → 这不是边缘情况，是主路径。

### 7.3 五组调参实验全灭（血的教训）

在发现 bug 前按常规思路调的，**没有一组让战斗变快**：

| 变体 | 改动 | 单轮均值 | 撞时限 | 预期 | 实际 |
|------|------|---------|--------|------|------|
| `aura_off` | 光环 12% → 0 | 42.9s | 70/160 | 变快 | **无变化** |
| `hp2` | hpMul 4 → 2 | 57.0s | 113/160 | 变快 | **更慢** |
| `atk35` | atkMul 2.2 → 3.5 | 44.3s | 78/160 | 变快 | **更慢** |
| `atk50` | atkMul → 5.0 | 47.0s | 87/160 | 变快 | **更慢** |

### 7.4 复现方法（零污染 A/B）

```bash
# 复制产物 → 改 FLAGS/数值 → 写到临时目录 → 指向它跑
GAME_HTML=<变体.html> node tests/arena_balance.js 60
```
