## A1. 像素网格对齐（P0-1，8h）—— 最值的一刀

### A1.1 问题诊断

现状 `render.js` 直接 `ctx.fillRect(x, y, w, h)` 任意浮点坐标 + `applyWorld` 连续缩放，结果：
- 高分屏（DPR 2.0）下边缘发虚，出现半像素灰边
- "开罗味"不成立——开罗的灵魂是**每个像素都落在网格上**
- 截图缩小到商店缩略图尺寸（300×180）时糊成一团

### A1.2 规格

```js
// config.js 新增
const ART = {
  PX: 2,                    // 1 个"美术像素" = 2 个世界单位
  scaleSteps: 9,            // 透视缩放量化档数（projS 从连续 → 9 档）
  snapTranslate: true,      // 世界坐标 translate 量化开关
};
```

**为什么 PX = 2 而不是 3 或 4**（rationale，不是拍脑袋）：

| PX | 单位高度（像素块） | 世界宽 1000 的网格数 | 评价 |
|---|---|---|---|
| 1 | ~50 | 1000 | 太细，等于没对齐，看不出像素感 |
| **2** | **~25** | **500** | ✅ 接近开罗的 24-32px 单位，**最优** |
| 3 | ~17 | 333 | 偏粗，头盔/武器细节会糊掉 |
| 4 | ~12 | 250 | 太粗，9 兵种辨识度崩 |

单位实测数据：`radius` 13-17，绘制高度约 50 世界单位 → PX=2 时**约 25 个像素块高**，与开罗《游戏开发物语》的角色比例（约 24-28px）一致。

### A1.3 技术细节（三个必须做对的点）

**① 量化 translate，不量化 scale —— 这是最容易做错的地方**

```js
// render.js · applyWorld 改造
function applyWorld(wx, wy) {
  const s = quantScale(projS(wy));      // ★ 缩放量化到 9 档
  const px = snap(wx), py = snap(wy);   // ★ 位置量化到 PX 网格
  ctx.translate(px, py);
  ctx.scale(s, s);
}

const snap = v => Math.round(v / ART.PX) * ART.PX;

function quantScale(s) {
  // projS 值域 [0.62, 1.16]，量化到 9 档，步长 0.06
  const lo = 0.62, step = 0.06, n = ART.scaleSteps;
  const k = Math.round((s - lo) / ((1.16 - lo) / (n - 1)));
  return lo + Math.min(n - 1, Math.max(0, k)) * ((1.16 - lo) / (n - 1));
}
```

> **为什么 scale 也要量化**：如果 scale 连续，同一个单位从远处走近时**大小会连续变化**，网格上的像素块会不断跨格 → 出现"抖动/呼吸感"，比不对齐还难看。
> 9 档是实测取舍：档位太少（如 5 档）近大远小的纵深感会变成"跳变"；太多（如 20 档）等于没量化。

**② 关掉图像平滑（数字 Draw 的硬件平滑）**

```js
// loop.js 初始化
ctx.imageSmoothingEnabled = false;
```
> 现状未设置 → 浏览器默认开启平滑 → 像素边缘被插值成灰边。**这一行是免费的，但必须加。**

**③ DPR 处理：不要按 DPR 放大画布**

现状 `verify_r14.js` 已处理高分屏缩放。改造要点：
```js
// 画布按 DPR 放大，但所有绘制坐标仍在"逻辑像素"空间，
// 由 setTransform(dpr,0,0,dpr,0,0) 统一缩放 —— 保证 PX=2 的对齐关系不被 DPR 打乱
canvas.width  = cssW * dpr;
canvas.height = cssH * dpr;
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
```

### A1.4 验收

| 检查 | 方法 | 通过线 |
|---|---|---|
| 边缘无半像素 | 截图放大 400%，检查单位轮廓 | 无灰色插值边 |
| 无抖动 | 录屏单位从远到近走动 | 大小跳变 9 次，其间稳定不抖 |
| 高分屏 | DPR 2.0 截图 | 与 DPR 1.0 观感一致 |
| **关掉能跑** | `ART.snapTranslate = false` | 游戏正常（回归到现状观感） |

## A2. 调色板系统（P0-2，12h）

### A2.1 问题诊断

现状 `BODY` / `BODY_DARK` 是 **60+ 个手写散色**（2 阵营 × 9 类型 × 2 明度），加上 `KAIRO` 表里每级的 `w1/w2/trim/metal`，总数 **150+ 个硬编码色值**。
后果：改配色要改 20 处；未来做皮肤/DLC 主题无从下手；不同兵种的"明暗关系"不一致。

### A2.2 规格：32 色主板 + 阵营 ramp

```js
// config.js 新增 PALETTE
const PALETTE = {
  // ── 中性/共用（8 色）──
  ink:        "#14100c",   // 描边（替代 OUTLINE 的 rgba）
  inkSoft:    "#2a2119",   // 次级描边/阴影
  skin:       "#f2c49b",   // 皮肤亮
  skinDark:   "#c98f66",   // 皮肤暗
  bone:       "#e8e0d0",   // 骨/牙/白布
  stone:      "#8a8578",   // 石材
  wood:       "#8a5a30",   // 木材亮
  woodDark:   "#5d3c1e",   // 木材暗

  // ── 金属（6 色）── 所有武器/头盔的金属部分从这里取，不许另写
  metalRaw:   "#8a7a68",   // 生铁（Lv1 洞穴人）
  metalBronze:"#c9a227",   // 青铜（Lv2）
  metalIron:  "#a8b4c4",   // 铁（Lv3）
  metalSteel: "#d6e2ee",   // 钢（Lv4）
  metalGold:  "#ffd479",   // 金（Lv5 / 晋升）
  metalDark:  "#4a5468",   // 暗部金属

  // ── 阵营 · 玩家（蓝系 6 阶 ramp）──
  p1: "#0e4a7a", p2: "#1660a8", p3: "#2a7fc4",
  p4: "#42a5f5", p5: "#7cc4ff", p6: "#c4e6ff",

  // ── 阵营 · 敌军（红系 6 阶 ramp）──
  e1: "#6e1410", e2: "#a01f1c", e3: "#d1382f",
  e4: "#ef5350", e5: "#ff8a7a", e6: "#ffd0c8",

  // ── 系别标识色（3 色，用于头顶标记/卡片描边）──
  typeMelee:   "#ff9f3a",
  typeRanged:  "#4fc3f7",
  typeCavalry: "#c084fc",

  // ── 功能色（5 色）──
  hpGood:  "#5ac84f", hpWarn: "#e8c86a", hpBad: "#e05a4f",
  gold:    "#ffd479", shield: "#7fd8ff",
};
// 共 32 色
```

### A2.3 迁移规则（ramp 的取值纪律）

原 `BODY.player.melee = "#42a5f5"` 这类**主色** → 取 `p4`（中亮，正面主体）。
`BODY_DARK.player.melee = "#1660a8"` → 取 `p2`（暗部，用于腿/手臂/侧身）。

**通用规则（所有单位适用）**：

| 部位 | 取 ramp 的第几阶 | 理由 |
|---|---|---|
| 躯干正面 | 第 4 阶（p4/e4） | 主体，最亮的一块，视线焦点 |
| 躯干侧面/手臂 | 第 3 阶（p3/e3） | 比正面暗一档，出体积 |
| 腿 / 后侧 | 第 2 阶（p2/e2） | 最暗，压住重心 |
| 高光 / 描边内侧 | 第 5 阶（p5/e5） | 只在受击闪白或晋升时用 |
| 屏幕最暗处阴影 | 第 1 阶（p1/e1） | 地面投影 |

> **为什么用 ramp 而不是继续散色**：一旦所有部位按 ramp 取色，**换阵营配色只需改 6 个值**，换整套主题（如"赛博朋克 DLC"）只需替换 `p1..p6` / `e1..e6` 这两组——这是未来做皮肤的前提。

### A2.4 `KAIRO` 表的迁移

现状每条 `KAIRO[type][level]` 有 `w1 / w2 / trim / metal` 四个色。改为**引用色板 key**：

```js
// 现状
{ helm:"bronze", weapon:"sword", w1:"#d6e2ee", w2:"#8a6a3a", trim:"#c9a227", metal:"#c9a227" }

// 迁移后（引用 key，不写字面值）
{ helm:"bronze", weapon:"sword",
  w1:"metalSteel", w2:"wood", trim:"metalBronze", metal:"metalBronze" }
```

**文明史的"材质递进"靠 metal ramp 表达**（这是设计意图，不只是换色）：

| 等级 | 文明阶段 | 材质色 | 视觉叙事 |
|---|---|---|---|
| Lv1 | 洞穴人 | `metalRaw` 生铁 + `wood` | 石头木棒，寒酸 |
| Lv2 | 青铜 | `metalBronze` | 有金属了，文明起步 |
| Lv3 | 铁器 | `metalIron` | 制式装备 |
| Lv4 | 火器/近代 | `metalSteel` | 精钢，工业感 |
| Lv5 | 机甲/未来 | `metalGold` + 发光 | 金色 + 高光，"我熬出头了" |

> **P2 支柱「军团成长可见」靠这条 ramp 兑现**：玩家不用看数字，看材质就知道自己到哪个时代了。

### A2.5 验收

| 检查 | 方法 | 通过线 |
|---|---|---|
| 色值收敛 | `grep "#" src/config.js \| wc -l` | 从 150+ 降到 ≤ 60（含 PALETTE 自身 32） |
| 换肤可行性 | 把 `p1..p6` 全换成绿色系，重 build | 玩家全军变绿，无残留蓝色 |
| 明暗一致 | 9 兵种并排截图 | 各兵种躯干/腿的明暗关系一致 |

## A3. 帧动画表（P1-1，24h）

### A3.1 问题诊断

现状 `kairoLeg(ctx, ox, oy, ang, ...)` 中 `ang` 来自程序化正弦 —— 走路是"匀速摆动"，没有**重量感**。
开罗风的动作之所以可爱，是因为它是**有限帧的循环**（一般 2-4 帧），每一帧都有明确的姿态。

### A3.2 规格：5 类动画 × 统一帧表

```js
// config.js 新增
const ANIM = {
  // 每帧 { legL, legR, armL, armR, bodyY, bodyRot } 的偏移/角度
  // bodyY: 躯干上下位移（像素块）；角度单位：度
  idle:  { fps: 4, loop: true,  frames: [
    { legL: 0,   legR: 0,   armL: 0,   armR: 0,   bodyY: 0,  bodyRot: 0 },
    { legL: 0,   legR: 0,   armL: -4,  armR: -4,  bodyY: 1,  bodyRot: 0 },  // 呼吸下沉
  ]},
  walk:  { fps: 8, loop: true,  frames: [
    { legL: -22, legR:  22, armL:  18, armR: -18, bodyY: 0,  bodyRot: 0 },  // 左腿前
    { legL:  0,  legR:   0, armL:   0, armR:   0, bodyY: -1, bodyRot: 0 },  // 过渡（身体略抬）
    { legL:  22, legR: -22, armL: -18, armR:  18, bodyY: 0,  bodyRot: 0 },  // 右腿前
    { legL:  0,  legR:   0, armL:   0, armR:   0, bodyY: -1, bodyRot: 0 },  // 过渡
  ]},
  attack:{ fps: 12, loop: false, frames: [
    { legL: 0,   legR: 0,   armL:  0,  armR: -60, bodyY: 0,  bodyRot: -8 }, // 抬手蓄力
    { legL: 0,   legR: 0,   armL:  0,  armR:  35, bodyY: 0,  bodyRot:  10 },// 挥出（过冲）
    { legL: 0,   legR: 0,   armL:  0,  armR: -10, bodyY: 0,  bodyRot:  0 }, // 回位
  ]},
  hit:   { fps: 20, loop: false, frames: [
    { legL: 0,  legR: 0,  armL: -20, armR: -20, bodyY: 2,  bodyRot: -12 },  // 后仰
    { legL: 0,  legR: 0,  armL:   0, armR:   0, bodyY: 0,  bodyRot:  0 },
  ]},
  death: { fps: 10, loop: false, frames: [
    { legL: 0,   legR: 0,   armL: -30, armR: -30, bodyY: 0,  bodyRot: -20 },
    { legL: -15, legR: -15, armL: -60, armR: -60, bodyY: 3,  bodyRot: -45 },
    { legL: -30, legR: -30, armL: -90, armR: -90, bodyY: 6,  bodyRot: -75 },
    { legL: -35, legR: -35, armL: -95, armR: -95, bodyY: 7,  bodyRot: -85 },// 倒地，转 drawCorpse
  ]},
};
```

**关键设计点**：

| 点 | 规格 | 理由 |
|---|---|---|
| **attack 的"过冲"帧** | 第 2 帧 `armR: +35`（超过目标位）再回弹 | 没有过冲 = 动作软。这是动画 12 原则里的 Overshoot |
| **walk 的过渡帧** | 4 帧而非 2 帧，含 2 个过渡帧 | 2 帧走路会像"滑行"；有过渡帧才有踩地的重量 |
| **hit 的 bodyY +2 / rot -12** | 受击时身体下沉并后仰 | 让"挨打"在没有音效时也能被看见（P1 支柱） |
| **fps 差异** | idle 4 / walk 8 / attack 12 / hit 20 | 快速动作帧率高 = 干脆；idle 帧率低 = 悠闲 |

### A3.3 与坐骑的协同

现状 5 种坐骑（boar/horse/ironhorse/moto/rex）各有独立腿动画。规格：

- **坐骑的腿相位与骑手错开 180°** —— 否则看起来像连体
- 坐骑 `walk` 用**自己的 4 帧表**（`ANIM_MOUNT`，四足动物的腿序是 左前-右后 / 右前-左后 交替，不是左右摆）

```js
const ANIM_MOUNT = {
  walk: { fps: 8, loop: true, frames: [
    { legs: [ 20, -20, -20,  20] },  // 四足：[左前, 右前, 左后, 右后]
    { legs: [  0,   0,   0,   0] },
    { legs: [-20,  20,  20, -20] },  // 对角步态
    { legs: [  0,   0,   0,   0] },
  ]},
};
```

### A3.4 验收

| 检查 | 方法 | 通过线 |
|---|---|---|
| 走路有重量 | 静音录屏 10 秒走路 | 能看出"踩下去"的瞬间 |
| 攻击干脆 | 单帧截图 attack 第 2 帧 | 武器明显挥出，有过冲 |
| 坐骑不连体 | 骑兵录屏 | 马腿与骑手相位错开 |
| 性能 | 80 单位同屏 | 帧率不低于改造前 |

## A4. UI 皮肤（P0-3，24h）

### A4.1 问题诊断

现状 UI 是原生 DOM + `style/*.css`（521 行）。做得规整，但：
- 面板是纯 CSS 圆角矩形，**没有开罗风的"厚边框 + 内嵌高光"**
- 按钮缺少明确的 4 态（normal / hover / active / disabled）
- 图标部分是 emoji（⚡ ✚），与像素风冲突

### A4.2 规格：9-slice 面板

**面板结构（开罗风的四个特征，缺一不可）**：

```
┌─ 外描边 ────────────────────────┐  ← 2px ink（PALETTE.ink）
│ ┌─ 主体填充 ──────────────────┐ │
│ │ ┌─ 顶部内高光（1px 亮色）─┐ │ │  ← 制造"凸起"的错觉
│ │ │                          │ │ │
│ │ │        内容区            │ │ │
│ │ │                          │ │ │
│ │ └─ 底部内阴影（1px 暗色）─┘ │ │  ← 制造"凹陷"的错觉
│ └────────────────────────────┘ │
└────────────────────────────────┘
```

实现方式（**保持单文件，不引外部图片**）：用 CSS `border-image` + 内联 SVG data URI，或者纯 CSS 多层 `box-shadow`：

```css
/* style/theme.css · 面板基础类 */
.panel {
  background: #241d16;
  border: 2px solid #14100c;
  border-radius: 4px;                    /* 小圆角，不要大圆角（大圆角 = 现代扁平风，不是开罗） */
  box-shadow:
    inset  0  2px 0 rgba(255,255,255,.10),   /* 顶部内高光 */
    inset  0 -2px 0 rgba(0,0,0,.35),         /* 底部内阴影 */
    inset  2px 0 0 rgba(255,255,255,.05),
    inset -2px 0 0 rgba(0,0,0,.20),
    0 3px 0 rgba(0,0,0,.40);                 /* 外投影，制造"厚" */
}
```

### A4.3 按钮 4 态（必须齐全）

| 态 | 规格 | 说明 |
|---|---|---|
| normal | 面板基础 + 主体色 | — |
| hover | 整体提亮 8% + 上移 1px | 用 `filter: brightness(1.08)`，不要另写色值 |
| active | **下沉 2px** + 去掉外投影 | 关键：**按下去要有"陷进去"的物理感** |
| disabled | 降饱和到 40% + 亮度 -20% | 现状置灰方式保留，但加 `cursor: not-allowed` |

```css
.btn { transition: transform .06s, filter .06s; }        /* 60ms，快但不瞬移 */
.btn:hover  { filter: brightness(1.08); transform: translateY(-1px); }
.btn:active { filter: brightness(.92);  transform: translateY(2px);
              box-shadow: inset 0 2px 0 rgba(0,0,0,.40); }
.btn:disabled { filter: saturate(.4) brightness(.8); cursor: not-allowed; }
```

> **60ms 的 transition 是刻意值**：0ms 太生硬，150ms 以上会觉得"迟钝"。
> 按钮手感是玩家点击频率最高的反馈通道（买兵一点就是几十次），值得单独调。

### A4.4 图标集（替换 emoji）

现状 `COMMANDS` 用 `icon: "⚡" "✚"`。emoji 的问题：不同平台渲染不同（Windows/Mac/iOS 字形不一致），且是彩色矢量，与像素风打架。

**规格：内联 SVG 图标，16×16 网格，走 `currentColor`**

| 图标 | 用途 | 网格 |
|---|---|---|
| ⚡ → `ico-strike` | 落雷 | 16×16，锯齿折线 |
| ✚ → `ico-heal` | 治疗波 | 16×16，粗十字 + 外圈 |
| `ico-freeze` | 冰封 | 六角雪花 |
| `ico-fire` | 火墙 | 三簇火焰 |
| `ico-rally` | 冲锋号 | 号角 + 声波 |
| `ico-decoy` | 诱饵 | 人形虚影 |
| `ico-gold` | 金币 | 圆形 + 内圈星 |
| `ico-wall` | 城墙 | 砖块纹理 |
| `ico-tech` | 科技 | 齿轮 + 上升箭头 |
| `ico-econ` | 经济 | 建筑 + 金币 |

实现方式：一个 `ICONS` 对象存 SVG path 字符串，`build.js` 时内联。
**保持单文件、零外部请求。**

### A4.5 验收

| 检查 | 方法 | 通过线 |
|---|---|---|
| 面板一致性 | 抽查 20 处面板 | 描边/圆角/投影偏差 ≤ 1 处 |
| 按钮手感 | 连点 20 次买兵 | 每次都有明确的"按下-弹起" |
| 图标跨平台 | Windows / Mac 各截一张 | 完全一致（SVG 不受字体影响） |
| 禁用态明确 | 钱不够时看买兵按钮 | 一眼看出点不了 |

## A5. 字体（P0-4，6h · 法律风险项）

### A5.1 风险等级：🔴 最高（唯一会吃官司的美术项）

### A5.2 方案对比与推荐

| 方案 | 授权 | 像素味 | 结论 |
|---|---|---|---|
| 系统默认（微软雅黑/苹方） | ✅ 无风险 | ❌ 违和 | 临时可用，不可上线 |
| **思源黑体 Source Han Sans** | ✅ **SIL OFL 1.1，明确商用** | ⚠️ 需像素化处理 | ✅ **推荐保底** |
| 方正像素 / 汉仪像素 | ⚠️ 需商业授权（年费） | ✅ 最好 | 有钱再买 |
| Zpix / Fusion Pixel | ⚠️ **需逐字核实**（部分 OFL，部分含限制） | ✅ 好 | 核实后可用 |

### A5.3 推荐落地方案

**第一步（保底，0 成本）**：思源黑体 + 像素化处理

```css
@font-face {
  font-family: "GameFont";
  src: local("Source Han Sans SC"), local("Noto Sans CJK SC"),
       local("Microsoft YaHei"), sans-serif;
}
body { font-family: "GameFont", sans-serif; }

/* 像素化处理：小字号下关掉次像素渲染，让边缘发硬 */
.ui-text, .hud-text {
  -webkit-font-smoothing: none;      /* macOS */
  font-smooth: never;                 /* 标准 */
  text-rendering: geometricPrecision;
}
```

**第二步（提升，可选）**：采购像素字体，控制在 ¥2,000 以内。
采购前必须：① 确认授权范围含"游戏内嵌 + 商业发行"；② 保存授权证书到 `docs/legal/fonts/`。

### A5.4 字号阶梯（像素风必须整数倍，否则发虚）

| 用途 | 字号 | 行高 |
|---|---|---|
| HUD 数值 | 12px / 14px | 1.2 |

## A6. 特效库 · 打击感三件套（P1-2，12h）

### A6.1 为什么这一节存在

自动对战的"爽"有一半来自视觉反馈。**P1 支柱「看得懂的混乱」要求：关闭音效后，玩家仍能"感觉到"每一次打击。**

现状已有 `hitStopMs: 120`（仅大招触发）。需要补三样：

### A6.2 命中闪白（hit flash）

```js
// drawUnit 内：受击后 0.09s 内，用亮色覆盖绘制
if (u.hitFlashT > 0) {
  ctx.globalCompositeOperation = "lighter";
  绘制单位轮廓，填充 rgba(255,255,255, .55 * (u.hitFlashT / 0.09));
  ctx.globalCompositeOperation = "source-over";
}
```

| 参数 | 值 | rationale |
|---|---|---|
| 时长 | 0.09s | <0.06s 看不见；>0.15s 会盖住后续动作 |
| 强度 | 55% 白 | 太高会"过曝"，在 30v30 时白屏 |
| **普通攻击也要有** | ✅ | 现状只有大招有顿帧，普攻是"静默"的 |

### A6.3 顿帧分级（hit-stop）

现状 `hitStopMs: 120` 是**全局统一值**。改为按伤害分级：

| 伤害等级 | 判定 | 顿帧 | 附加 |
|---|---|---|---|
| 普通命中 | dmg < 1.5×atk | **0ms** | 只闪白（否则 30v30 会变成幻灯片） |
| 重击 | 1.5× ≤ dmg < 3× | 60ms | 闪白 + 轻微拖尾 |
| 暴击/克制 | dmg ≥ 3× 或触发克制 | 100ms | 闪白 + 拖尾 + 屏震 2px |
| 大招/处决 | 技能或反应表 | 160ms | 全屏闪 + 屏震 6px + 推近（P3） |

> **为什么普通命中不给顿帧**：30v30 时每秒发生 30+ 次普攻，每次停 120ms → 游戏直接卡成 PPT。
> 现状的 120ms 之所以没出问题，是因为它只在**大招**时触发（大招频率 ~2 次/秒）。**分级是必须的，不是优化。**

### A6.4 击退拖尾（knockback trail）

击退（`knock`）时，在单位后方留 3 个逐渐透明的残影：

```js
// 残影：位置取自单位最近 3 帧的历史坐标，透明度 0.4 / 0.25 / 0.12
```
> 成本：每个被击退单位多 3 次绘制。用 `compact` 对象池控制上限（最多同时 20 个单位有拖尾）。

### A6.5 屏震分级

| 事件 | 幅度 | 时长 |
|---|---|---|
| 普通攻击 | 0 | — |
| 重击 | 1-2px | 0.08s |
| 大招 | 4-6px | 0.15s |
| 炸药桶爆炸 | 8px | 0.2s |
| 城墙崩塌 | 12px | 0.35s |

**红线：屏震总幅度不超过 12px，且同一时间只取最大值不叠加。** 否则晕眩。

## A7. 场景分层与视差（P1-3，10h · 第一个可砍项）

### A7.1 现状

`drawGround()` 画天空/远山/地面三层，全部静态。

### A7.2 规格：三层视差

| 层 | 内容 | 视差系数 | 说明 |
|---|---|---|---|
| 远景 | 天空渐变 + 云（`drawCloud` 已有） | 0.1 | 几乎不动，云自己缓慢飘 |
| 中景 | 远山（`drawHill` 已有） | 0.3 | 轻微跟随 |
| 近景 | 地面 + 城墙 + 单位 | 1.0 | 主战场 |

视差跟随镜头（若未来加镜头移动）或跟随鼠标（**镜头不动时，用鼠标位置驱动 ±8px 的轻微视差**，成本极低，观感提升明显）。

### A7.3 前景遮挡物（可选，+4h）

在屏幕最下方画一排半透明的草丛/旗帜剪影，不遮挡战场（只占最底部 40px）。
作用：制造"窥视战场"的临场感。

> **砍项判定**：若 M3 排期吃紧，A7 整节（10h）第一个砍。**它不改变玩法，只增加观感。**
