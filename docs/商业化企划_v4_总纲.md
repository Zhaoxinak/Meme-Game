# 第一部分 · 战略

## 0. 一句话结论（先给答案）

**这游戏现在缺的不是机制，是"商品的外壳"和"回来的理由"。**

代码实测显示：战斗骨架（2.5D 投影 / 三元环 / 六分支 / 粒子池 / 双模式）已经扎实，v3 守城经济也跑通了。但**音乐为 0、存档为 0、Meta 为 0**——这三样恰好是"玩家明天还来不来"的全部答案。

所以 v4 的资源分配是反直觉的：

```
音频 25%  ████████  从 0 建起来，每 1 小时投入的体验增益最高
美术 30%  ██████████  像素对齐 + 调色板 + UI 皮肤，把"像开罗"变成"是开罗"
机制 25%  ████████  只做 6 个（v2 设计了 15 个），砍掉 9 个
商业 10%  ███  只埋架构位，不接 SDK
工程 10%  ███  多端适配 + 埋点 + 性能预算
```

**最大的判断：v2 那 15 个机制不是"3 个月计划"，是"内容上限"。全做完要 9 个月，3 个月只能做 6 个。砍是有理由的砍，不是偷懒。**

### 1.3 缺口 ❌（按严重度排序）

| # | 缺口 | 实测证据 | 商用影响 | 严重度 |
|---|---|---|---|---|
| 1 | **无 BGM，无音频总线** | `audio.js` 仅 50 行；`grep BGM/bgm/music` → **0 命中** | 打开游戏 3 秒内的"完成度感知"直接崩。这是**最便宜也最致命**的短板 | 🔴 致命 |
| 2 | **无任何存档** | `grep localStorage` → **0 命中** | 没有 Meta、没有解锁、没有累计 → **没有第二天回来的理由** | 🔴 致命 |
| 3 | **v2 的 15 个机制全在纸面** | `FLAGS`/`props`/`weather`/`morale`/`director`/`veteran`/`formation`/`cp` → **全部 0 命中** | 战斗深度停留在"点两个技能看兵互殴" | 🟠 高 |
| 4 | 指令只有 2 条 | `COMMANDS` 数组仅 `strike` / `heal` | 参与感不足，30 分钟里玩家真正在"决策"的时间太少 | 🟠 高 |
| 5 | 美术无像素网格对齐 | `render.js` 直接 `fillRect` 任意坐标，无 PX 网格 | 高分屏下发虚，"开罗味"不成立，截图不吸量 | 🟠 高 |
| 6 | 无调色板系统 | `BODY`/`BODY_DARK` 是 60+ 个手写散色 | 改配色要改 20 处；未来做皮肤/DLC 主题无从下手 | 🟡 中 |
| 7 | 无动画帧表 | 腿部为程序化正弦摆动 | 动作没有"重量感"，打击反馈弱 | 🟡 中 |
| 8 | 无埋点与数据 | 无任何统计代码 | 无法验证留存/难度曲线，调参靠猜 | 🟡 中 |
| 9 | 无字体方案 | 走系统默认字体 | 中文在像素风里违和；且**商用字体有版权风险** | 🟡 中（法律风险） |
| 10 | 单文件 206 KB，未做加载态 | 打开即渲染 | 未来加 BGM 音频后首屏会白屏 | 🟢 低 |

> **审计结论**：这是一款"系统完成度 65%、商品完成度 25%"的项目。
> 系统侧（战斗/经济/分支）已经能跑 20 波；商品侧（听感/观感/留存/数据）几乎为零。
> **v4 全部火力集中在商品侧。**

## 2. 市场定位与竞品格局

### 2.1 市场数据（2026 实测）

| 指标 | 数值 | 来源 |
|---|---|---|
| 微信小游戏 MAU | **5 亿+**（开发者 50 万+） | 2026 微信小游戏开发者大会 |
| 小程序游戏市场规模 | **535.35 亿元**（2025），同比 **+34.39%** | 中国游戏产业年会 / 艾瑞 |
| 模拟经营品类增速 | **+210%**（IAP 增速第一） | 2026 微信小游戏大会 |
| 塔防 / 放置品类 | 历史注册 3-5 亿，付费用户 1000-2000 万 | 同上 |
| PC 小游戏 | MAU **+10%**，其中 **40% 为 PC 独占用户**；在线时长翻倍、付费 ARPPU 翻倍 | 同上 |
| IAA 分成激励 | 50% 现金 + 最高 40% 广告金 = **最高 90%** | 同上 |
| IAP 新游激励 | 首发期 **5000 万元流水不分成** | 同上 |

**这组数据对"网页优先"策略的意义**：
- PC 小游戏 40% 独占用户 + 时长翻倍 + ARPPU 翻倍 → **网页/PC 端玩家质量远高于移动端**，而网页版正是这个项目的天然主场（单文件 HTML、零安装）。
- 模拟经营 +210% → 本作的"守城经营"恰好踩在这条增速最快的赛道上。
- **结论：网页版不是"退而求其次"，是精准卡位。**先吃 PC 端高质量用户，再移植移动端拿量。

### 2.3 差异化定位（Design Positioning Statement）

> **"开罗的皮，自走棋的骨，塔防的心。"**

| 维度 | 本作的位置 | 为什么这个位置是空的 |
|---|---|---|
| 美术 | 开罗像素风——**一眼可辨识的品牌符号** | 开罗社自己不做对战；做对战的（TFT/云顶）都是重度 3D |
| 玩法骨架 | 自动对战——**零操作门槛** | 自走棋品类已被验证（Backpack Battles 100 万份） |
| 玩法血肉 | 波次守城 + 金融运营——**钱怎么花决定守到第几波** | 塔防品类增速快但都是"摆塔"；本作是"养军团" |

## 3. 产品定义

### 3.1 Fun Hypothesis（一句话，所有设计的地基）

> **看着自己那支从洞穴人一路进化到机甲的军团，在自动团战里用一发落雷引爆墙前的炸药桶、把半个屏幕的敌人炸飞——是这游戏好玩的核心。**

拆成三个可验证的要素：
1. **成长的可见性**：军团从 3 人 → 30+ 人，从棒子 → 机甲
2. **爆发的爽感**：连锁反应、一击清场
3. **经营的掌控感**：钱怎么花决定守到第几波

> 这三条任何一条做不出来，都不该往下走。§12 的 Playtest 失败信号就是围绕这三条设计的。

### 3.2 Design Pillars（5 条，不可妥协）

| # | Pillar | 含义 | 违反它的反例 |
|---|---|---|---|
| **P1** | **看得懂的混乱** | 30v30 混战里，玩家 1 秒内能看清"谁在打谁、谁快死了" | 满屏特效盖住单位，看不清战况 |
| **P2** | **军团成长可见** | 每一次升级/晋升/买兵，画面上立刻看得见 | 数值涨了但外观不变，全靠数字跳动 |
| **P3** | **钱永远不够花** | 四选一，买兵/科技/城墙/经济互相打架，没有唯一解 | 攒钱无脑买满，或某条线是必选 |
| **P4** | **对称即公平** | 敌我同一套规则；玩家的赢来自决策，不来自隐藏加成 | 玩家侧常驻增伤（历史上连杀 +30% 把 50:50 推成 71:29，已修） |
| **P5** | **沙雕但不廉价** | 幽默来自机制翻车（弹射板把友军弹进敌阵），不是网络烂梗 | "起飞！""yyds" 这类梗文案（现有 `BIGWORDS` 已守住这条） |

### 3.3 三层循环

```
┌─ Moment-to-moment（0-30 秒）────────────────────────────────┐
│  动作：放指令 / 买兵 / 切驻守-出击 / 调倍速                    │
│  反馈：命中闪白 + 顿帧 120ms + 击退拖尾 + 飘字                 │
│  奖励：金币 +5、大招触发、状态反应连锁                         │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─ Session loop（25-35 分钟 · 守城一局）───────────────────────┐
│  目标：守住这一波 → 张力：钱不够、墙快破了 → 结果：波次结算      │
│  每 5 波一个 Boss 波硬门槛，逼你提前 2 波准备                   │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─ Long-term（数天 - 数周）────────────────────────────────────┐
│  ❶ Meta 天赋树（军师/通讯/后勤…只影响指挥力，不给属性）         │
│  ❷ 图鉴解锁（见过/用过每一个兵种与分支）                       │
│  ❸ 每日挑战（固定种子，全服同题，排行榜）                      │
│  ❹ 名场面集锦（自动保存高光帧，可分享）                        │
└─────────────────────────────────────────────────────────────┘
```

**⚠️ 长线循环现在完全是空的。** 现状 `localStorage` 零引用 = 玩家打完一局，什么都不留下。
**这是 v4 必须解决的第二优先级问题（仅次于音乐），否则DAU 次日留存不会有结构性改善。**

## 5. 美术企划（决策层，规格见附录 A）

### 5.1 核心判断：不要换成贴图，要"把矢量画成像素"

现有 988 行程序化绘制是**资产，不是负债**。它带来了：零素材依赖、单文件 206 KB、改一处 `node build.js` 即生效、无 404 风险。
**推倒重来去做 sprite sheet 是错的**——那会破坏这个项目的核心优势，且一人团队扛不住几百张图的产能。

正确做法是**三刀，全部低风险高回报**：

| 刀 | 改什么 | 成本 | 收益 |
|---|---|---|---|
| **① 像素网格对齐** | 引入 `PX = 3`（世界像素单位），所有 `fillRect` 坐标 `Math.round(x/PX)*PX` | ~40 行 + 全局替换 | **"开罗味"从 0 到 80%**。这一刀最值 |
| **② 调色板收敛** | 60+ 个散色 → 32 色主板 + 每阵营 8 色 ramp，改色只改 `PALETTE` | ~120 行重构 | 未来做皮肤/DLC 主题只改一处 |
| **③ 帧动画表** | 程序化正弦 → 关键帧表（idle 2 / walk 4 / atk 3 / hit 1 / death 4） | ~200 行 | 动作有重量感，打击反馈成立 |

### 5.2 美术优先级（P0 必做 / P1 做 / P2 有余力）

| 级别 | 项目 | 工时 | 理由 |
|---|---|---|---|
| **P0-1** | 像素网格对齐 | 8h | 一分钱不花，观感提升最大的一刀 |
| **P0-2** | 调色板系统重构 | 12h | 是一切皮肤/主题的前置条件 |
| **P0-3** | UI 皮肤（9-slice 面板 + 按钮 4 态 + 图标集） | 24h | 商用观感的门面；现在是原生 DOM 样式 |
| **P0-4** | 字体方案（**必须解决版权**） | 6h | 法律风险，不能拖到上线前 |
| **P1-1** | 帧动画表（5 类 × 全部单位复用一套骨架） | 24h | 手感来源 |
| **P1-2** | 打击感三件套（闪白 / 顿帧分级 / 拖尾） | 12h | 战斗爽感的一半在视觉反馈 |
| **P1-3** | 场景分层与视差（前景/中景/远景） | 10h | 画面纵深，截图吸量 |
| **P2-1** | 状态图标与描边（配合 §7 状态系统） | 8h | 依赖机制，机制上才做 |
| **P2-2** | 宣传物料（图标 / 截图 / GIF） | 8h | 上线前 2 周集中做 |

**美术总工时 ≈ 112h**。按 12 周 × 每周 20h = 240h 的总盘，占 **47%**——偏高。
**因此 P1-3 场景视差（10h）应作为第一个被砍的项**，若排期吃紧优先保 P0 与 P1-1/P1-2。
> 修正后美术工时目标 **≤ 96h（40%）**，机制与音频不能被挤掉。

### 5.3 字体版权（法律风险，必须现在定）

| 方案 | 授权 | 风险 | 建议 |
|---|---|---|---|

## 6. 音乐与音频企划（决策层，规格见附录 B）

### 6.1 这是最短的板，也是性价比最高的投入

现状：`audio.js` **50 行**、13 个 `tone()` 振荡器音效、无 BGM、无总线、无音量控制。

**玩家打开游戏的前 8 秒**，如果安静，感知就是"这是个 demo"。
BGM 是**唯一一个能在 1 周内（~30h）把"完成度感知"从 25% 拉到 50% 的单项投入。**

### 6.2 音频目标架构

```
                    ┌─ Master Bus（总音量，持久化到 localStorage）
                    │
        ┌───────────┼───────────┐
    BGM Bus       SFX Bus     UI Bus
    (0.45)        (0.70)      (0.55)
        │             │           │
   ┌────┴────┐   45 个音效    按钮/面板音
 7 首 BGM   分层 stem
 (低/中/高)
```

三条总线的**存在理由**（不是为做而做）：
- **BGM / SFX 分离**：这是玩家投诉率第一的问题（音乐盖过打击声，或反之）。独立的默认音量 0.45 / 0.70 是刻意的不对等——**打击音效必须比音乐响**，否则自动对战的"爽"出不来。
- **UI Bus**：UI 音要轻（0.55），因为它的触发频率是音效的 10 倍（每次买兵、点按钮），响一点就烦。

### 6.3 BGM 曲目表（7 首）

| # | 曲目 | 使用场景 | 时长 | BPM | 情绪 | 优先级 |
|---|---|---|---|---|---|---|
| 1 | **主菜单 · 军团集结** | 主菜单 | 60-75s 循环 | 100 | 轻快、期待感 | **P0** |
| 2 | **守城 · 备战** | 波间喘息（interWave 5s）+ 低强度 | 45-60s 循环 | 92 | 舒缓、算计 | **P0** |
| 3 | **守城 · 交战** | 战斗中（默认层） | 60-90s 循环 | 124 | 紧张推进 | **P0** |
| 4 | **守城 · 铁壁告急** | 城墙任一段 HP < 30% | 60s 循环 | 136 | 危机、急促 | **P1** |
| 5 | **Boss 波 · 巨影压境** | 第 5/10/15/20 波 | 60-75s 循环 | 140 | 压迫、史诗 | **P0** |
| 6 | **竞技场 · 快攻** | 竞技场模式 | 45-60s 循环 | 140 | 明快、街机 | **P1** |
| 7 | **结算 Sting**（胜/负各一条） | 结算画面 | 3-5s 一次性 | — | 胜利=上扬 / 失败=下坠 | **P0** |

**为什么是 7 首而不是 15 首**：一人团队 + AI，每首曲子从 prompt 迭代到可用（含对齐循环点、导出、接入、实测）约 **4h**。7 首 = 28h，正好一个里程碑。**先做 P0 的 5 首（20h）**，P1 两首留到 M3 有余力再补。

### 6.4 动态音乐（P1，但架构现在就要留位）

守城模式天然有三段强度：**备战 → 交战 → 告急**。

| 强度层 | 触发条件 | 音乐变化 |
|---|---|---|
| 低 | `G.phase === "interwave"` 或场上敌人 ≤ 3 | 只有 pad + 低音（去掉鼓和旋律） |
| 中 | 战斗进行中，城墙三段 HP 均 > 30% | 全编制（默认层） |
| 高 | 任一段城墙 HP < 30% 或 Boss 波 | 加鼓组 + 铜管，BPM 不变但密度上升 |

**实现成本**：每首曲子导出 3 个 stem（drums / bass+pad / lead），运行时按层淡入淡出。
**架构现在就要留位**（`playBgm(key, layer)` 接口先定义好），即使 M1 只实现"整曲切换"——否则以后重做要改所有调用点。

### 6.5 音效：13 → 45 个

现状 13 个音效全部是单音符 `tone()`，听感是"电子表"。商用级需要**分层合成 + 随机变体**。

| 类别 | 数量 | 代表音效 | 现状 |
|---|---|---|---|
| UI | 10 | 按钮悬停 / 点击 / 买兵成功 / 买不起（deny）/ 页签切换 / 面板开合 | 仅 `deny` 1 个 |
| 战斗 | 18 | 挥砍 / 命中（3 种材质变体）/ 弓弦 / 枪响 / 激光 / 爆炸 / 冲锋马蹄 / 击退落地 / 死亡（3 变体） | 6 个（hit/shoot/boom/thud/bounce/skill） |
| 经济 | 8 | 金币入账 / 征税 / 升级完成 / 建筑落成 / 城墙受击 / 城墙崩塌 / 利息结算 / 波次结算 | 0 |
| 演出 | 9 | 大招蓄力 / 大招释放 / 名场面大字 / 晋升 / 传说陨落 / 罐头笑声 / 胜利号角 / 失败音 / 连杀提示 | 4 个（skill/cheer/laugh/win/lose） |

**关键技术要求：所有高频音效必须有 3 个变体**（音高 ±80 cents 随机 + 轻微时长抖动）。
理由：同一个"命中"音在一场 30v30 战斗里要响几百次，**没有变体会直接变成噪音**，这是自动对战品类特有的、必须提前解决的设计问题。

### 6.6 音乐版权路径（一人 + AI 团队的唯一可行解）

## 7. 机制企划：从 15 个砍到 6 个

### 7.1 为什么必须砍

v2 企划设计了 15 个机制，全部基于现有代码底座，每个都合理。**但它们是"内容上限"，不是"3 个月计划"。**

按实测代码量估算，v2 全量落地 ≈ **1,300+ 行逻辑 + 350 行 UI + 对应美术演出**，约 **200h**。
而 3 个月一人 + AI 的总盘只有 **240h**，还要分给美术（96h）和音频（60h）。

**机制能分到的只有约 80h。必须砍。**

### 7.2 取舍标准：每个机制回答三个问题

1. **它制造了什么新的玩家决策？**（答不出 = 只是数值膨胀，砍）
2. **它是地基吗？**（是地基 = 后续内容的成本被摊薄，优先）
3. **关掉它游戏还能跑吗？**（不能 = 耦合太深，风险高，后做）

### 7.3 决策结果

#### ✅ 做（6 个，约 78h）

| # | 机制 | 工时 | 决策理由 | 落地阶段 |
|---|---|---|---|---|
| **M1** | **存档系统 + Meta 天赋树** | 18h | **不是机制，是留存的地基**。`localStorage` 现在零引用，没有它玩家打完什么都不留下。天赋只影响"指挥力"（CP 上限/CD/开局 CP），**红线：不给属性加成** | M1 |
| **M2** | **状态系统（6 状态）+ 反应表** | 14h | **唯一的真地基**。落雷、新指令、新兵种、天候全要"往单位身上挂点什么"。有了它，内容量是**乘**的；没有它，每个新内容都是一次性的 | M2 |
| **M3** | **指挥点 CP + 指令扩到 6 条** | 16h | 把"到 CD 就按"变成"资源管理"。从 2 条扩到 6 条（+冰封/火墙/冲锋号/诱饵），玩家每场开始排技能顺序 | M2 |
| **M4** | **战场物件层（炸药桶 + 补给箱 + 治疗泉）** | 14h | **本作最爽的 3 秒**：敌人扎堆拆墙 → 落雷点桶 → 链式核爆清场。复用现有 `aoeAt`，成本极低 | M2 |
| **M5** | **名场面导演（Director）** | 8h | **UGC 传播素材的制造机**。这是 §2.3 差异化定位的落点，也是最便宜的获客手段 | M3 |
| **M6** | **老兵晋升（击杀累积 → 外观变化）** | 8h | **P2「军团成长可见」支柱的直接兑现**。演出价值极高、实现极简（只改 `drawUnit` 描边 + 一个计数器） | M3 |

#### ⏸ 延后到 v5（6 个）

| 机制 | 砍的理由 |
|---|---|
| 天候时间轴 | 体验增量大但 **110 行 + 每套天候要配套演出**；且天候是"被动接受"，不制造决策，性价比低于 CP |
| 敌方指挥官 AI | **必须与 M3 指令扩容成对上线**（不做就破坏对称），但 AI 调参是时间黑洞。M3 先上，AI 放 v5 |
| 特殊编制（医师/爆破手/法师…） | **200 行 + 6 套新美术**。守城模式已经有爆破手/医师/法师（`SHOP.units`），竞技场侧优先级低 |
| 战前布阵三选一 | 只改坐标，成本低（70 行），但**与 M3 的 CP 系统抢同一个"回合开始"UI 位置**，同时上会让界面过载 |
| 士气系统 | 好设计，但和 M1 的"背水一战"橡皮筋（`ECON.rubberLoseStep`）**功能重叠**，先验证现有橡皮筋够不够 |
| 占点与超时判定 | 改判定逻辑，**风险最高**（可能让守城模式的"龟缩流"重新变成最优解），需要大样本 playtest 支撑 |

#### ❌ 明确不做（3 个）

| 机制 | 砍的理由 |
|---|---|
| 指挥官上场与光环 | 守城模式没有"后排"概念（敌人从右边来），指挥官站位逻辑与守城骨架冲突 |
| 三角阵羁绊 | 纯奖励、无决策，且和 P1「看得懂的混乱」打架（满屏连线更看不清） |
| 镜像模式 | 是**平衡测试工具**，不是玩家内容。作为内部测试模式保留，不占玩家入口 |

### 7.4 机制验收：对称自检清单（每个机制上线前必答）

沿用 v2 §0.1，但加一条针对守城模式的：

1. 敌人能不能用？（不能 → 违反 P4 对称原则）
2. 它加的是**抉择**还是**白赚**？（白赚 → 随机选也能赢，决策失效）
3. 它会让某一条线变成唯一解吗？（会 → 收敛数值）
4. 关掉它游戏还能跑吗？（不能 → 耦合太深，重做）
5. **🆕 守城模式下它会不会让"龟缩流"重新变成最优解？**（会 → 重做）
   > 加这一条的历史原因：v3 曾因驻守流无解，被迫加"攻城巨兽"反制。任何新机制都可能重新打开这个口子。

## 8. 商业化架构（只埋位，不接 SDK）

### 8.1 现状判断：现在不该定商业模式

用户明确"先做品质，模式待定"。这是对的——**网页版的核心任务是验证留存，不是验证付费**。

但架构位现在就要留，否则以后接 SDK 要伤筋动骨。

### 8.2 预留的四个架构位（M1-M2 埋，不激活）

| 架构位 | 实现 | 成本 | 什么时候激活 |
|---|---|---|---|
| **① 货币双轨** | `G.meta = { soft: 军功, hard: 勋章 }`，对局只产出 soft | 2h | 定变现模式时 |
| **② 皮肤挂载点** | `unit.skin` 字段 + `kit(u)` 读 skin 覆盖默认配色 | 4h | 做皮肤系统时 |
| **③ 激励视频钩子** | `Ads.requestReward(type)` 空实现，预留 4 个点位 | 3h | 接广告平台时 |
| **④ 商品配置表** | `IAP_ITEMS` 空数组 + 统一的购买流程函数 | 3h | 定内购时 |

### 8.3 未来变现点位设计（先设计好，等数据再激活）

> **原则：不卖数值，只卖时间、外观和爽感。** P4「对称即公平」是红线，卖数值等于自杀。

| 点位 | 类型 | 设计 | 为什么不破坏平衡 |
|---|---|---|---|
| **复活续关** | 激励视频 | 主城破后看广告 → 主城回 50% HP，继续这一波 | 只给一次机会，且给的是"重来"不是"变强" |
| **双倍波次奖励** | 激励视频 | 波次结算时看广告 → 本波金币 ×2 | 不改变战斗过程的对称性 |
| **皮肤（兵种外观）** | 内购 | 机甲线"霓虹"皮肤、近战线"三国"皮肤 | **纯外观，零数值**（由架构位②保证） |
| **去广告** | 内购 | 一次性买断 | 标准做法 |
| **离线收益** | 月卡 | 挂机收税上限提升 | 加速不破平衡，符合"卖时间"原则 |

**明确不做**：抽卡、开箱、体力、战力礼包。
理由：本作的爽点是"军团成长与战术决策"，抽卡会把玩家的注意力从"我怎么打赢"转移到"我抽到什么"——**这是两个不同的游戏**，混在一起两边都做不好。

### 8.4 变现的前提：先有数据

| 里程碑 | 数据目标 | 达标后才做 |
|---|---|---|
| 网页版上线 4 周 | 次日留存 ≥ 25%，7 日留存 ≥ 10% `[PLACEHOLDER]` | 才值得接移动端的量 |
| 网页版上线 8 周 | 单局完成率 ≥ 60%（守城 20 波） | 才值得做内购 |
| 12 周 | 平均单局时长 25-35 分钟（对齐设计目标） | 才值得做月卡 |

> 这些数字是**[PLACEHOLDER]**，取自放置/塔防品类的经验区间。
> **在拿到真实数据之前，任何变现决策都是赌博。**

## 9. 工程与技术

### 9.1 多端适配路径（网页优先 → PC 小游戏 → 移动端）

| 阶段 | 平台 | 关键工作 | 工时 |
|---|---|---|---|
| **M0-M3** | 网页（单文件 HTML） | 保住"双击即开"；加加载态；加埋点 | 12h |
| **M3+** | **微信/抖音小游戏** | 包体拆分（首包 ≤ 4MB）、BGM 改远程加载、接平台 API | 40h（v5） |
| **M3+** | **Steam** | Electron/打包、成就、云存档、商店页 | 60h（v5） |
| **M3+** | 移动端 | 竖屏重排 + 触控热区放大 | 50h（v5） |

**为什么 PC 小游戏排在移动端前面**（数据支撑）：PC 端 40% 独占用户 + 时长翻倍 + ARPPU 翻倍，而本作单局 25-35 分钟 —— **这是一个"坐下来玩"的游戏，天然属于 PC 端**。移动端适配（竖屏重排）工作量最大、收益最不确定，放最后。

### 9.2 性能预算（硬红线）

| 指标 | 预算 | 实测现状 | 保护机制 |
|---|---|---|---|
| 同屏单位 | ≤ 50 敌 + 30 我 = 80 | `WAVE.maxAlive:50` ✅ | 溢出预算转敌人等级 |
| 帧率 | ≥ 55 FPS @ 1080p | 待测 `[PLACEHOLDER]` | `compact` 原地压缩 |
| 粒子数 | ≤ 420 | 已有池 ✅ | 对象池上限 |
| 单文件大小 | ≤ 3 MB（含音频） | 206 KB | 音频走外部加载 |
| 首屏时间 | ≤ 2s | 即时 | 加加载态后可延长到 3s |
| 内存 | ≤ 200 MB | 待测 | 音频 Buffer 复用 |

> **新增音频后的风险**：7 首 BGM 若全部内嵌 base64，单文件会涨到 3-5 MB。
> **对策**：BGM 走**外部文件 + 运行时加载**（网页版），或**小游戏端远程加载**。单文件纯净版保留"仅音效"降级模式。

### 9.3 埋点（网页版必须有，否则调参靠猜）

| 事件 | 关键字段 | 用来回答什么问题 |
|---|---|---|
| `game_start` | mode, difficulty, metaLv | 玩家选哪个模式？ |
| `wave_end` | wave, gold, armySize, wallHp[3], deaths | **玩家第几波流失最多**（最关键的一张图） |
| `purchase` | type(兵/科技/墙/经济), item, cost, wave | 钱都花在哪？四选一是否平衡 |
| `unit_buy` | unitType, count | 哪个兵种是必选？（唯一解检测） |

**最小可行埋点**：只做 `wave_end` 和 `game_end` 两个，6h 就能出第一张留存漏斗图。**先做这两个。**

## 11. Playtest 计划

### 11.1 先定义"坏掉长什么样"（没有失败定义的 playtest 等于没做）

| 失败信号 | 具体表现 | 诊断方向 |
|---|---|---|
| **A · 三分钟弃游** | 新玩家 3 分钟内关闭页面 | 前 3 波没有教会玩家；或 BGM/画面第一观感劝退 |
| **B · 看不懂克制** | 玩了 10 分钟说不出"近战克哪个" | 克制反馈不足（+35% 感知不到）→ 加视觉标记 |
| **C · 无脑解** | 超过 60% 的局选择了同一套兵种组合 | 涨价曲线失效 → 调 `SHOP.units[].scale` |
| **D · 中期疲惫** | 第 8-12 波流失率突增 | 难度曲线或经济增长不匹配 → 调 `WAVE.budgetGrowth` |
| **E · 指令闲置** | 全场指令释放 < 5 次 | CP 太紧或指令没存在感 → 调 `cpRegen` |
| **F · 龟缩流复活** | 驻守占比 > 80% 且胜率更高 | 攻城压力不足 → 加"攻城巨兽"或提高 `wallAtkMul` |
| **G · 静音率过高** | > 40% 玩家关掉音乐 | 曲目选错或循环太短 → 换曲/加长 |

### 11.2 三轮 Playtest

| 轮次 | 时间 | 人数 | 方法 | 主要验证 |
|---|---|---|---|---|
| **PT1 纸面/内部** | W5 末 | 3 人（含自己） | 玩 M1 版本 30 分钟，出声思考 | 失败信号 A、B、G |
| **PT2 小外部** | W9 末 | 8-12 人 | 网页链接 + 埋点 + 问卷 | 失败信号 C、D、E、F |
| **PT3 上线前** | W12 | 30+ 人 | 公开测试 + 完整埋点 | 全部信号，重点看留存漏斗 |

### 11.3 Monte Carlo 平衡推演（W7 必须做）

现有 `tests/sim.js` 已能做代理对战。扩展成**守城 20 波的批量推演**：

```
对每种策略代理（经济优先 / 兵力优先 / 科技优先 / 均衡），各跑 200 局
输出：每波的通过率、平均金币曲线、平均兵力曲线、失败波次分布
```

**用途**：在真人 playtest 之前先把数值区间收窄。真人测试是用来验证"手感"的，不是用来找"第 12 波数值崩了"的。

> 这一步的价值：**把 80% 的数值问题挡在 playtest 之前**。不做这一步，PT2 会发现一堆数值 bug，白白浪费 12 个人的时间。

## 14. 一句话总结（v4）

> 这款游戏的**骨头已经长好了**（战斗骨架 + 守城经济 + 三元环分支），**缺的是皮和魂**：
> **皮** = 像素对齐 + 调色板 + UI 皮肤（让"像开罗"变成"是开罗"）；
> **魂** = BGM + 音效总线（让打开游戏的前 8 秒就有完成度）+ Meta 存档（让明天还有理由回来）。
>
> **三个月的胜负手不在做多少机制，而在于前五周能不能把"声音"和"存档"这两块最短的板补上。**
> 补上了，剩下的机制可以一个一个长出来；补不上，机制做得再多也只是个没人回来的漂亮 demo。
