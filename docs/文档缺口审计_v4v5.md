# 文档缺口审计 · v4 + v5
## 2026-09-04 · 五份文档交叉核对结果

> **审计范围**：`商业化企划_v4_总纲.md` · `附录A_美术规格书.md` · `附录B_音频规格书.md` · `附录C_12周排期与验收门禁.md` · `战斗内容层深度设计_v5.md`
> **审计方法**：工时逐项加总核对 + 关键词覆盖率扫描 + 系统间依赖交叉验证。
>
> **一句话结论**：设计质量没问题，**账目和覆盖面有问题**。
> 最硬的一条：**五份文档合计需求 426 小时，而 3 个月只有 240 小时——差 186 小时，接近一倍。**

## A 类 · 硬矛盾（不修会导致执行错乱）

### A1 🔴 工时账三处打架，且总量装不下

| 来源 | 承诺线工时 | 备注 |
|---|---|---|
| 附录 C 逐项加总 | **184h** | 17 项明细，加总正确 |
| v4 §10.2 里程碑表 | **220h** | 56+44+60+60 |
| v4 §10.4 资源分配 | **186h** | 又是一个数 |

**v4 §10.2 的表内部也不自洽**（与附录 C 明细对比）：

| 里程碑 | v4 §10.2 | 附录 C 对应项加总 | 差额 |
|---|---|---|---|
| M0 听感 | 56h | 8+8+18+12+10 = **56h** | ✅ 一致 |
| M1 留存 | 44h | 存档8+天赋12+埋点6 = **26h** | **+18h** |
| M2 观感地基 | 60h | 像素8+调色板12+UI皮肤24+字体4 = **48h** | **+12h** |
| M3 深度与上线 | 60h | 状态10+反应4+CP16+打击感12+Playtest12 = **54h** | **+6h** |

> 差额合计 36h，推测是 v4 §10.2 预留了缓冲，但**没有写明**，导致三处数字互相对不上。
> **修法**：以附录 C 的 184h 为准，v4 §10.2/§10.4 改成 184h，并注明"含每周 2h 机动共 24h 已计入"。

**更严重的是总量**：

```
v4 承诺线   184h
v4 冲刺线    66h
v5 全部     176h
─────────────────────
总需求      426h
3 个月可用  240h  (12 周 × 20h)
─────────────────────
缺口        186h   ← 需要砍掉 44% 的工作量
```

**解法建议**（三选一，我推荐方案 A）：

| 方案 | 内容 | 结果 |
|---|---|---|
| **A · 分期（推荐）** | v5 只做 P0+P1+P2 = **58h**；英雄系统（P3-P6, 98h）整体延到第二阶段 | 总需求 308h，仍超 68h → 再砍冲刺线即可对齐 240h |
| B · 延长时间 | 3 个月 → 5.5 个月 | 保住全部内容，但错过窗口期 |
| C · 砍 v4 机制 | v4 的状态系统/CP 与 v5 对换优先级 | ❌ 不推荐：两个都要改 `damageUnit`，对换只会让返工翻倍 |

**为什么推荐 A**：英雄系统虽是内容亮点，但它依赖 §10 的 `damageUnit` 契约，
而 v4 的状态系统（W9）也要改同一个函数。**等 v4 把 `damageUnit` 定型再上英雄，能省掉一次返工。**
v5 的 P0（对称性修复 6h）和 P1（双轴克制 24h）性价比极高且不依赖契约，可以先做。

### A2 🟠 镜像试炼：v4 说不做，v5 当验收工具

| 文档 | 表述 |
|---|---|
| v4 §7.3 | ❌ **明确不做**："是平衡测试工具，不是玩家内容。作为内部测试模式保留，不占玩家入口" |
| v5 §5.6.3 | "双方同英雄同等级同强化，胜负 100% 由指挥决定" |
| v5 §8.1 | "镜像模式 200 局胜率 **50% ± 4%**" —— 作为**核心验收手段** |

**两者其实不冲突**（v4 说不占玩家入口，v5 用作内部工具），但 v4 那句"❌ 明确不做"
会让执行者以为**不用实现**，然后 v5 的验收就跑不起来。

**修法**：v4 §7.3 改为 ——
> ⏸ **不做玩家入口，但必须作为内部测试模式实现**（隐藏入口或 debug flag）。
> 它是验证 §0 对称性修复是否成功的唯一工具，见 v5 §8.1。

### A3 🟠 FLAGS 缺 v5 的全部开关

v4 §12.2 的 13 个 FLAGS 里，**没有一个属于 v5**。
按 v4 自己定的铁律（"任何一个 FLAG 关掉，游戏必须还能正常跑"），v5 的每个新系统都要有开关：

```js
// 需要补充（v5）

merc:       true,   // v5 §4.3.3 雇佣兵
recycle:    true,   // v5 §4.5 战地回收（新增 source）
```

## B 类 · 零覆盖模块（文档里完全没有）

### B1 🔴 新手引导 / Onboarding —— 覆盖率 0

| 扫描项 | 命中 |
|---|---|
| `tutorial` / `onboarding` | **0** |
| "引导" / "教学" | 2 处，均为顺带提及 |

**为什么这是致命的**：v4 §11.1 的**第一个失败信号就是"三分钟弃游"**，
而这套设计到 v5 为止，玩家需要同时理解：

```
三元环克制（近战→骑兵→远程）
+ 双轴克制（5 攻击 × 5 护甲）
+ 经济四选一（兵/科技/城墙/建筑）
+ 8 个特殊编制
+ 6 选 1 英雄（= 6 种流派）
+ 6 条指令 + 士气大招
+ 驻守 / 出击切换
```

**没有任何 onboarding 设计，新玩家在第 2 分钟就会被淹没。**

**建议的最小引导方案**（约 12h，进承诺线）：

| 波次 | 教什么 | 时长 | 手法 |
|---|---|---|---|
| W1 | 买 1 个兵 | ≤15s | 高亮买兵按钮，不买不能开始 |
| W2 | 近战克骑兵 | ≤10s | 首次遭遇骑兵时弹克制提示 |
| W3 | 驻守 / 出击 | ≤15s | 首次出现远程敌人时教驻守加成 |
| W5 | 英雄大招 | ≤15s | Boss 波士气满时，大招按钮脉冲发光 |
| W8 | 双轴护甲 | ≤15s | 首次出现重甲敌人时提示"用钝击" |

**三条纪律**：
1. **一次只教一件事**，教完立刻用上（教完买兵马上就要买）
2. 所有提示**可跳过**，且二周目不再出现（存 `SAVE_V1.tutorialDone`）
3. 不阻塞战斗——提示是浮层，不是模态弹窗

> **反面案例**：把 5×5 矩阵做成开屏教程图。玩家不会看，而且会直接关掉游戏。

### B2 🟠 可访问性 —— 覆盖率 0

| 风险点 | 现状 | 影响人群 |
|---|---|---|
| **阵营配色红 vs 蓝** | `BODY.player` 蓝系 / `BODY.enemy` 红系 | 红绿色盲（男性约 8%）**完全分不清敌我** |
| 克制飘字颜色 | 金/品红/浅绿/灰蓝/深灰 | 同上 |
| 字号 | 12-14px 固定 | 老花/小屏 |
| 音量 | 三总线（v4 已设计） | ✅ 已覆盖 |

**最低限度要做的两件**（约 6h）：
1. **阵营除颜色外，加形状区分**：玩家方单位底部加蓝色脚环，敌方加红色尖刺底座。
   或者更简单——**敌我朝向相反**（现状 `facing` 已经是 ±1，视觉上已可区分，需确认是否足够明显）。
2. **色盲模式开关**：设置面板加一档，把红蓝改成蓝/橙（色盲友好配色）。

> 这条不做，等于主动放弃 8% 的男性用户。而本作目标用户 45% 是"策略养成派"男性。

### B3 🟡 本地化 / 多语言 —— 覆盖率 0

v4 §9.1 规划了 Steam 上线（60h），但：
- 文案抽取方案：无
- 翻译流程：无
- 多语言字体：无（中文像素字体本身就是个未决风险，见附录 A §A5）

**现状判断**：**第一版不做多语言是合理的**（先验证中文市场）。
但要在 v4 §9.1 明确写一句"v1 仅简体中文，多语言排到 v6"，
否则执行者可能在写代码时硬编码中文字符串，到时候抽取成本翻倍。

**最低限度**（约 2h，现在就做）：把所有 UI 文案集中到一个 `STRINGS` 常量对象，
哪怕暂时只有中文。**这是零成本的预防。**

### B4 🟡 存档迁移 —— 覆盖不足

附录 C §C3 已经设计了 `version` 字段和 `migrate()` 骨架（这点做得对）。
但 v5 新增了大量持久化数据，迁移路径没写：

| v5 新增 | 存档影响 |
|---|---|
| 英雄选择 + 养成进度 | `SAVE_V1` 需要新增 `hero: { unlocked:[], levels:{} }` |
| 8 编制解锁状态 | 需要记录已解锁编制 |
| 教程完成标记 | `tutorialDone`（B1 需要） |
| 消耗品/雇佣兵购买记录 | 本波有效，可不存；但统计需要 |

**修法**：在附录 C 的 `migrate()` 里补一条规则——
**新增字段一律用"读取时补全默认值"**，而不是在 migrate 里逐个 if。

```js
function migrate(save) {
  save.hero ??= { unlocked: ["guardian"], levels: {} };   // v2 新增
  save.tutorialDone ??= {};                                // v2 新增
  save.codex ??= { seen: {}, used: {} };                   // v3 新增
  return save;
}
```

### B5 🟠 平衡模拟器 —— 只有口号，没有设计

| 文档 | 表述 |
|---|---|
| v4 §11.3 | "Monte Carlo 平衡推演（W7 必须做）" |
| v5 §5.5.2 | "Monte Carlo 跑 200 局" |
| v5 §8.1 | "镜像试炼 200 局胜率 50%±4%" |

**但现有 `tests/sim.js` 是竞技场 5 轮的模拟器**，守城 20 波的模拟器**不存在**。

没有模拟器 = 上面那些"跑 200 局"全部跑不出来 = 所有数值 PLACEHOLDER 无法收敛。

**建议**（约 16h，与 v5 P1 并行）：

```
tests/siege_sim.js
  ├─ 策略代理（4 种）：经济优先 / 兵力优先 / 科技优先 / 均衡
  ├─ 每代理跑 200 局，输出到 CSV
  └─ 输出指标：每波通过率、金币曲线、兵力曲线、失败波次分布

验收：能复现 v5 §5.5.2 的目标曲线
     第 5/10/15/20 波通过率 = 85% / 65% / 45% / 30%
```

> **这条的价值**：v4 §11.3 自己说了——"把 80% 的数值问题挡在 playtest 之前"。
> 没有它，PT2 会发现一堆数值 bug，白白浪费 12 个测试者的时间。

## D 类 · v5 内部可补强

### D1 🟡 商业化没接上英雄

v4 §8 设计了四个架构位（货币双轨/皮肤挂载点/广告钩子/商品配置表）。
**英雄是天然的变现载体，但 v4 §8.3 的点位表里一个英雄相关的都没有。**

| 可加的点位 | 类型 | 为什么不破坏平衡 |
|---|---|---|
| 英雄解锁 | 内购 / 军功 | 6 个英雄中 2 个免费，其余用军功解锁（可付费加速） |
| **英雄皮肤** | 内购 | **纯外观**，由 v4 §8.2 架构位②保证零数值 |
| 英雄养成加速 | 广告 | 看广告立即完成一次升级（省时间不省资源） |

> 注意 v4 §8.3 的红线仍然适用：**不卖数值**。英雄强度只能靠局内金币买。

### D2 🟡 性能预算未重估

v4 §9.2 定的是"≤50 敌 + 30 我 = 80 单位"。v5 之后需要重估：

| 新增开销 | 影响 |
|---|---|
| 双轴矩阵查表 | 每次伤害多一次 `AT_VS_ARMOR[a][d]` 查表 —— **可忽略**（二维数访问） |
| 8 编制 | 单位数可能突破 30（编制也占编制位） |
| 英雄 | +2 单位（敌我各 1），但绘制成本高（特效多） |
| **士气/大招特效** | **这是真开销**：6 种大招的全屏特效，同屏叠加时可能掉帧 |

**建议**：把"同屏特效实例上限"加入性能预算（建议 ≤ 8 个全屏级特效，超出排队或降级）。

### D3 🟡 英雄美术成本被低估

v5 §9 R7 说"复用 `kairo*` 装配系统 + 独立配色与披风，不做独立骨架"——**判断是对的**，
但附录 A 的工时表里**没有英雄美术这一项**（见 C 类，实际需要 16h）。
